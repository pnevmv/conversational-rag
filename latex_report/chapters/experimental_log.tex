\chapter{Experimental Log and Supplementary Results}\label{ax:log}

This appendix records how the experimental setup evolved before the final protocol
of Chapters~\ref{ch:llm_baseline} and~\ref{ch:rag}, the preliminary and negative
results obtained along the way, and supplementary result tables. Unless stated
otherwise, all runs use the same \gls{llm} deployment (\texttt{gpt-5.4-nano}) on the
\gls{mdd} validation split.


% ===========================================================================
\section{Evolution of the Retrieval Unit}\label{ax:log:indexing}

The first \gls{rag} experiments (\emph{v1}) indexed each document span
individually, giving a corpus of 35{,}659 spans. \gls{mdd} documents contain
heading spans (\texttt{h3}/\texttt{h4} tags) that carry only a heading string and no
answer content, for example ``How do I pay DIAL-IN Search Account fees?'' or ``How
will I know my application has been accepted?''. When such spans were retrieved at
the top rank, the generator received a heading without its answer and replied that
``the context only shows the heading''; this affected roughly a dozen of the 50 pilot
examples.

All pipelines were therefore re-run with \emph{section-level} indexing
(Section~\ref{sec:rag:arch}), which reduced the corpus to 4{,}114 sections and
improved \ratk{5} by a factor of 10--20 on the 50-example pilot set
(Table~\ref{tab:log:indexing}). With span-level indexing, hybrid retrieval
underperformed dense retrieval because the BM25 ranking was dominated by heading
spans; once BM25 became a competitive ranker over sections, fusion outperformed both
components.

\section{Preliminary 50-Example Experiments}\label{ax:log:pilot}

Before the dev-500 subset (Section~\ref{sec:dataset:dev500}) was introduced, all
pipelines were developed on a deterministic set of 50 consecutive user--agent turn
pairs from the validation split.

\subsection{Initial Prompts and the Single-Domain Pilot (v2)}

The first \gls{llm}-only prompt was a bare instruction (``Answer the following
question as accurately as possible. Question: \{question\}''). It obtained
0.00\% \gls{em} and 7.53\% token \fone{}: the model produced multi-paragraph
explanations, while the references are short agent utterances. It also
misinterpreted domain-specific questions. Asked ``My insurance ended so what should
I do'', whose reference is ``You will need to get insurance or we will suspend your
registration and license'', the model gave general health-insurance advice
(Healthcare.gov, COBRA, Medicaid), having no way to know that the question concerned
DMV vehicle registration.

The first \gls{rag} prompt (``You are a helpful assistant. Answer the question using
only the context provided below. If the context does not contain enough information,
say so briefly.'') was used for the v2 runs in Table~\ref{tab:log:v2}.

\subsection{Pipeline Fixes and the Balanced Pilot (v3/v4)}

Looking at the v2 runs led to five fixes. The loader went through the domains in
sorted order and reached the 50-example limit before leaving DMV, so the v2 set was
entirely DMV; sampling the domains in turn fixed this (DMV~13, SSA~13, StudentAid~12,
VA~12). About two thirds of the v2 \gls{rag} answers contained phrases such as ``the
context doesn't say'', bold text or bullet lists, which led to the agent-voice few-shot
prompt of Section~\ref{sec:rag:generation} with a fixed abstention phrase; the
\gls{llm}-only baseline uses the same voice without context. Each example is now tagged
as answerable or unanswerable, and \fone{} and the abstain rate are reported separately
for the two groups. Domain Recall@$K$ was added after pages from VA, SSA and StudentAid
were seen among the results for DMV questions. Finally, the evaluation script had the
experiment name hard-coded, so every output file had the wrong label.

The v3 run applied these fixes; v4 re-ran the same set after adding the
document-switch tag and the logging of top retrieval scores
(Table~\ref{tab:log:v4}). The lower recall compared with v2 reflects the harder
multi-domain setting: the balanced set contains more decontextualised follow-up
turns, and cross-domain vocabulary (``benefits'', ``disability'') lets BM25 retrieve
sections from the wrong domain.

On the nine document-switch turns of this pilot, \ratk{5} was 44.4\% (BM25),
22.2\% (Dense), 55.6\% (Hybrid) and 22.2\% (Hybrid+Rewrite), against 17.1\%,
41.5\%, 31.7\% and 56.1\% on same-document turns. This first suggested that the
rewriter pulls retrieval towards the previous document, a pattern confirmed at
full scale (Table~\ref{tab:rag:docswitch}).

\subsection{Abstention Detection}

Up to and including the full-split runs of Section~\ref{sec:rag:fullsplit}, an
answer counted as an abstention only if it matched the abstention phrase exactly.
From the dev-500 experiments onwards, a single shared function
(\texttt{is\_abstention}) counts any answer containing ``no relevant information''
(case-insensitive), which also catches minor rephrasings of the phrase.

\section{Score-Threshold Abstention: A Negative Result}\label{ax:log:threshold}

Since the pilot showed that better retrieval reduced abstention (BM25 abstained on
67\% of unanswerable turns, Hybrid+Rewrite on none), a retrieval-side abstention
gate was tested: if the top-1 retrieval score falls below a threshold, the system
returns the abstention phrase without calling the \gls{llm}. Each retriever exposes
its own score: raw BM25 (about 0--30 on this corpus), cosine similarity for dense
retrieval (about 0.5--0.9), and the RRF score for hybrid retrieval (about
0.016--0.034).

The gate does not work for hybrid retrieval with or without rewriting. On the pilot,
unanswerable examples obtained RRF scores of 0.0323--0.0328, at or above the
answerable median (0.0320), so any threshold that catches the unanswerable examples
also abstains on most answerable ones. Rewriting makes queries specific enough to
always find plausible-looking context. The gate is more viable for BM25, where an
unanswerable question sometimes shares no term with any section. The conclusion is that
abstention needs a generation-side mechanism, such as an \gls{llm} sufficiency check,
rather than a retrieval score gate.

    \toprule

    \midrule

              paying Dial-in search account fees apply?'' \\
    ``What are the fees for that?'' & ``What are the fees for DMV call center
              exemptions in New York City?'' \\
    ``Where can I find more info?'' & ``Where can I find more information about
              New York DMV vehicle registration insurance requirements?'' \\

              identification for DMV requirements?'' \\
    \bottomrule
\end{tabular}
\end{center}

The remaining retrieval failures after rewriting fell into two groups: turns where
the dialogue itself is underspecified, so that even the rewritten query stays vague
(e.g.\ ``how to clear up DMV issues and update address after receiving a letter''),
and turns whose answer spans several sections that do not all fit in the top five.

\section{Compute and Runtime}\label{ax:log:runtime}

\gls{llm} calls run in a thread pool with retry and exponential back-off on
rate-limit errors, and every response is cached on disk under a hash of its prompt.
With 12 workers, the first run of the six original pipelines on dev-500 took
17.1~minutes; subsequent runs are served from the cache in seconds. The four
pipelines of the prompt-v2 and reranker ablations took 20.3~minutes in total, of
which cross-encoder scoring of the 25{,}000 (query, section) pairs took
12.5~minutes on CPU (\texttt{bge-reranker-base}, batch size 256). Reranker scores
are cached separately, keyed by a SHA-256 hash of the query and section text.
Building the dense index (4{,}114 sections) takes about 15--30~seconds on Apple MPS
and is cached on disk.
